# Что такое Release Conveyor Kit - объяснения на разных уровнях

Документ-ответ на вопросы "что это / как работает / зачем нужно" для разной
аудитории. Полезен и как заготовка для лендинга/презентации.

## Аналогия в одну строку

Ты сам(а) написал(а) книгу (приложение). Кит - это типография с конвейером:
берёт твою рукопись и сам печатает, переплетает, проверяет на опечатки и
развозит по магазинам. Книгу пишешь ты, всё остальное делает конвейер.

## Ребёнку (~10 лет)

**Что это.** Представь, ты слепил из конструктора крутую игру. Теперь её надо
показать друзьям: положить в коробку, проверить что ничего не отвалилось,
отнести в магазин игрушек. Кит - это волшебный помощник-робот, который всё это
делает за тебя каждый раз, когда ты что-то поменял в игре.

**Как работает.** Ты говоришь роботу один раз, как твоя игра устроена. Дальше,
как только ты меняешь игру, робот сам: проверяет, что она не сломалась,
складывает в коробку и относит в магазин. Если что-то отвалилось - робот машет
красным флажком и не пускает поломку к друзьям.

**Зачем нужно.** Чтобы не делать скучную работу руками каждый раз и чтобы
друзьям никогда не попала сломанная игра.

## Взрослому-нетехнарю (вайбкодит наликтовыванием в чат ИИ)

**Что это.** Ты в чате с ИИ собрал работающее приложение - это здорово, но это
только половина дела. Вторая половина - "выпуск": проверить, что новая версия
не сломала старое, собрать установочный файл, выложить в App Store / Google Play
/ на сайт, и следить, чтобы у людей оно не падало. Обычно это недели возни с
непонятными настройками. Кит - это готовый набор этих настроек плюс инструкция
для твоего ИИ-агента, как их применить к твоему приложению.

**Как работает.** Ты не разбираешься в деталях. Ты говоришь своему ИИ-агенту:
"примени вот этот Кит". Агент задаёт тебе несколько простых вопросов (как
называется приложение, нужен ли Android/iPhone, есть ли аккаунты), потом сам
расставляет все технические файлы по местам и проверяет, что всё работает. Где
нужна твоя рука (например, завести аккаунт разработчика и заплатить за него) -
агент даёт короткий список "сделай эти 3 шага".

**Зачем нужно.** Чтобы приложение, которое ты навайбкодил, реально доехало до
людей и работало стабильно - без того, чтобы ты месяц учил DevOps. Из "у меня
на компе работает" в "лежит в сторе и обновляется само".

## Взрослому, понимающему ИТ-процессы, но без опыта сборки обвязок

**Что это.** Поставляемый релизный слой (CI/CD + мониторинг + сторовые процессы)
для конкретного стека: React/TS + Vite + Capacitor + Supabase + Vercel, CI на
GitHub Actions и Codemagic. Не стартер нового приложения, а "обвязка поверх уже
существующего MVP". Поставляется как шаблоны с плейсхолдерами + промпты для
ИИ-агента, который их применяет.

**Как работает.** Один конфиг `conveyor.config.json` параметризует всё (имена,
идентификаторы, ветки). 8 независимых модулей (CI, мобильные сборки, выкладка в
сторы, окружения, мониторинг, секреты, smoke-тесты, агентный слой). Агент
прогоняет интервью -> детект стека -> применяет модули по порядку -> проверяет
каждый по чек-листу -> отдаёт отчёт "что применено / что проверено / что руками".
Принципы: идемпотентность (повторное применение не ломает), config-first,
секреты только плейсхолдерами, ничего не пушится без зелёной проверки.

**Зачем нужно.** Потому что собрать эту обвязку с нуля - это недели чтения
документации по каждому инструменту и куча граблей (подпись Android, SPM в
Capacitor 8, шардинг Playwright, утечки секретов). Кит даёт уже пройденный путь:
ту же обвязку, что реально работает в боевом проекте, за вечер вместо
недель.

## Айтишнику

**Что это.** Извлечённый из продакшена релизный pipeline,
обобщённый в applicable kit: набор GitHub Actions workflows, codemagic.yaml,
Sentry-инициализация, Playwright smoke, gitleaks, паттерн QA-окружений на
free-tier Supabase - всё параметризовано через единый конфиг и применяется
агентным сценарием (AGENTS.md + apply-kit.md).

**Как работает.** Скоуп жёстко зафиксирован одним стеком (React/TS + Vite +
Capacitor + Supabase + Vercel + GH Actions + Codemagic) - это и есть стратегия:
не мультистек-комбайн, а глубокая поддержка одного знакомого стека. Модули:
1. ci-core - lint+unit+build на PR, кэш, concurrency.
2. mobile-build - Android AAB/APK с подписью через injected gradle props,
   versionCode=run_number; iOS на Codemagic, Capacitor 8 = SPM (App.xcodeproj,
   без CocoaPods/workspace).
3. store-deploy - Google Play + TestFlight, автоматизация где API стабилен,
   иначе пошаговые инструкции (модуль 3 держится в инструкциях намеренно - сторы
   меняют требования).
4. staging - вариант A (второй проект/branch) или вариант B (тегированные
   QA-аккаунты + SECURITY DEFINER RPC очистки под JWT пользователя, без service
   role в CI).
5. monitoring - Sentry (release-теги через define из package.json, sourcemaps
   через @sentry/vite-plugin, beforeSend-редакция apikey), health-check cron.
6. secrets - .env/.gitignore паттерны, gitleaks с allowlist, карта секретов.
7. smoke-e2e - Playwright, auth через Supabase REST (без UI, sub-секундный
   setup), 7 сценариев с TODO-метками.
8. agent-layer - инварианты + сценарий применения + шаблон отчёта.

Идемпотентность через CREATE OR REPLACE / merge-not-overwrite, верификация по
чек-листам как gate перед push, честная классификация результата
(verified / unverified / manual / skipped).

**Зачем нужно.** Снять с владельца проекта недели DevOps-плумбинга и убрать
класс ошибок, которые уже один раз были пройдены и задокументированы. Бонус:
сам процесс самопроверки кита нашёл 3 бага (gitleaks PR permissions,
health-эндпоинт, vitest/playwright collision) - это и есть продуктовое знание.

## Сценарий: "у меня нет проекта, есть только идея"

Честная граница: **Кит v0 - это релизный слой поверх УЖЕ существующего
приложения, а не генератор приложения с нуля.** Если у тебя только идея, Кит
сам по себе приложение не создаст - ему нечего "обвязывать". Но он встаёт
ровно во вторую половину пути. Полный маршрут такой:

### Шаг 1 - навайбкодить MVP (без Кита)

Идея превращается в работающий минимальный продукт обычными vibe-coding
инструментами: Lovable, Bolt, v0, Cursor, Claude Code. Главное - чтобы на выходе
был тот самый стек: React + Vite + TypeScript, данные в Supabase. Это 1-2
вечера на простое приложение.

Пример. Идея: "приложение для учёта домашних растений и напоминаний о поливе".
Вайбкодишь: список растений, добавить/удалить, отметить полив, логин. Оно
работает у тебя на `npm run dev`. Это и есть MVP.

### Шаг 2 - применить Кит (вот тут он и помогает)

Теперь приложение есть, но: нет автосборки, нет выкладки в стор, нет
мониторинга, секреты раскиданы, тестов нет. Открываешь сессию ИИ-агента в папке
проекта и говоришь "примени Release Conveyor Kit". Агент:
- спрашивает: как называется, нужен ли Android, есть ли аккаунты, какая главная
  сущность (у тебя - "растение");
- расставляет workflows, настраивает Sentry, пишет smoke-тесты под твои экраны,
  закрывает секреты;
- прогоняет проверку и отдаёт отчёт + список "заведи вот эти аккаунты и секреты".

Результат: каждый твой пуш проверяется и собирается сам, приложение едет в стор,
падения видны в Sentry. Из "работает на моём ноуте" в "живёт в продакшене".

### Что нужно от тебя, простыми словами

1. Иметь работающий MVP на нужном стеке (или навайбкодить его - шаг 1).
2. Аккаунты: GitHub (бесплатно), Supabase (бесплатно), для сторов - Google Play
   ($25 разово) и/или Apple Developer ($99/год), по желанию Sentry (бесплатно
   на старте), Vercel (бесплатно).
3. Запустить агента с Китом и ответить на вопросы интервью.
4. Сделать ручные шаги из финального отчёта (в основном - вставить секреты и
   нажать пару кнопок в консолях).

### Юзкейсы

- **Владелец кита (v0):** новые твои проекты поднимаются за вечер, а не за недели -
  это и есть первая цель Кита.
- **Муж / знакомый вайбкодер:** навайбкодил MVP, релизить руками не умеет и не
  хочет - даёт своему агенту Кит, получает рабочий конвейер, к чужому коду ты
  доступа не получаешь (применяет агент владельца).
- **Будущий платный клиент:** "у меня MVP в Lovable, хочу в App Store и чтобы
  не падало" - Кит ровно про это.

### Если хочется "из идеи в один клик" (вне скоупа v0)

Технически на этапе самопроверки уже создавался минимальный чистый скелет
(Vite+React+TS+Supabase) - то есть стартер-заготовку Кит породить может. Сделать
из этого режим "Кит создаёт и пустой проект, и обвязку" - реалистичное
расширение, но это отдельная фича: в v0 намеренно не делаем, чтобы не
размывать скоуп.
